# 技能族全生命周期测试方法

## 公开投影

公开发布时，生成器把本文投影为插件内与各 Skill 同目录的 `references/testing-methodology.md`。运行包内副本不能单独改；修订身份仍为 `design-testing-methodology@0.1.1`。


## 目的、职责与要求来源

本方法用于明确技能族在每轮迭代中应测试的内容、测试方式、判定标准及停止条件。覆盖范围包括方案设计、资产组织、执行组织、结果核收与复测。项目采用时须明确所依据的方法和规范，技能族自身差异与接受判据应保留在其独立制品中。

- **skill-family-test**：负责组织测试活动，识别测试范围与执行路径。
- **Foundation**：提供公共技术检查项、原生宿主校准能力与通用验证支持。
- **目标族或独立验收职责持有方**：负责业务层面的接受判断，掌握领域答案。
- **skill-family-audit**：负责规范适用性审查与独立规范合规性核验。

skill-family-test 可由项目在日常开发中独立调用，负责测试方法、执行组织与覆盖判断，不依附发布流程。发布流程仍沿用项目原有路径，测试通过不自动赋予发布授权。不引入 Loop 机制，不恢复 skill-eval，也不复制已有执行器、验证器或领域规则。

测试要求来自目标族业务承诺、正式适用规范、现有强制门禁，以及调用方提供的阶段要求；发布场景的对象、范围和阶段要求由 release-skill 提供。测试职能将这些要求逐项承接到方案，确定本次执行、有效复用或有依据的不适用，保留未覆盖和未完成项。未映射、缺判据或相互冲突的要求须交还原权威处理，不得默认为免测；只选中部分发布单元也不自动免除项目级义务。测试职能可选择检查方法与受影响范围，不能自行改变业务承诺或强制要求。沿现有方案引用，不另建义务注册表。

## 测试分层与交付阶段

脚本、LLM 与人工是执行方式，非测试层级。各测试层级需明确以下四要素：

- 测试对象  
- 检查方法  
- 结果判定依据  
- 实际覆盖范围  

| 环节 | 测试职能职责 | Foundation 支持内容 | 目标族保留事项 |
|------|--------------|----------------------|----------------|
| 需求与方案 | 明确业务承诺、必测项、复用理由、停止条件 | 提供能力目录、适用条件与接入支持 | 保留业务风险评估、判据定义与接受责任 |
| 单元与组件 | 验证受影响逻辑及其边界回归 | 提供公共合同、已有向量与替身支持 | 保留领域算法、脚本逻辑与参数策略 |
| 集成与接线 | 从真实公共入口验证对象、参数、组合及失败传播 | 提供公共函数与输入输出合同 | 保留消费者接线逻辑与业务结果一致性 |
| 候选载荷与静态检查 | 确定实际包、路径与宿主执行面 | 提供清单、路径、闭包、投影与范围内加载规则 | 保留本次载荷配置与定制接线策略 |
| 宿主与环境 | 确定受影响阶段，调用检查或核验复用证据 | 提供承诺宿主的安装、更新、发现、加载检查及实机校准支持 | 保留宿主特有接线与未覆盖差异 |
| 真实业务与人工验收 | 执行真实 Skill 正常路径、风险相关失败路径，必要时人工判读 | 提供已有调用准备、路径约束与进程监督 | 保留模型与工具协作逻辑、业务语义、视觉或交互结果 |
| 文档可用性 | 组织按文档安装和使用的适用验证，由领域或专业职责判断效果 | 提供适用的公共检查与调用支持 | 保留使用场景和接受判据；公开材料、版本与发布要求一致性仍由发布方核对 |
| 发布核收 | 交接有效结果、候选身份与未决项 | 提供对应工程证据支持 | 保留原有发布门禁与批准流程 |

Foundation 的目标是通过复用校准后的公共部分，减少重复实机测试。实际覆盖不足时，应明确缺口，不能据此缩小上述职责。静态语法检查、原生发现或加载、模型选择并完成任务，三者结论不同，不可混用。不能以共享静态检查证明全部业务成功，也不要求其穷尽所有模型行为。

测试方案区分三种交付阶段，避免把开发回归和稳定验收混为一谈：

| 阶段 | 接受范围 |
|------|----------|
| 开发基线 | 围绕当前开发承诺验证功能和回归风险，不默认追加独立验收。 |
| 候选交付 | 按候选合同验证适用范围，可以保留明确的未验证项，但不得据此宣称稳定业务验收通过。 |
| 稳定业务验收 | 验证对外稳定承诺及其接受条件；需独立验收的部分使用隔离材料，候选状态不能替代该阶段的结论。 |

阶段区别用于选择测试和解释结论，不新增状态机或批准流程。

## 按真实用户条件验证 E2E

1. 测试须从正式公开的 Skill 入口启动，仅提供业务目标、必要材料、真实运行环境与授权，以及预期交付成果要求，不附加隐藏答案、内部通关路径；本次用户实际提出的业务要求与必要步骤均应保留，确保路径与实际使用场景一致。

2. 严格遵循公开合同条款与业务权限边界，执行发布前审批等必要流程；测试中允许被测 Skill 在授权范围内自主查阅资料、澄清疑问、纠错、重试或采用等效替代路径，不强制工具使用顺序，不限定尝试次数，亦不要求必须先犯特定错误；测试结果判定应综合业务目标达成情况与必要过程执行完整性，二者缺一不可。

3. 被测技能的开发与独立验收必须分离，产品失败记录须完整保留；负责人修复后须针对修订后的对象复测受影响部分，不得更改判定标准或替换版本以掩盖失败；未执行关键环节不得认定为完整通过。所有额外限制（如禁用某工具、限定尝试次数）必须基于真实用户行为记录、公开合同条款或当前业务风险依据，测试便利性不得作为设置限制的理由。

允许使用隔离测试工程、虚构材料及测试账户，但须明确其代表的用户场景与实际覆盖范围；单元、集成与故障专项测试可精确设定条件，但须分别说明验证目标与实际覆盖范围，不得替代普通用户路径；未触发工具报错时，不得宣称已验证报错恢复能力，该专项状态应保留为“待验证”。

## 选测、复用与停止

首次基线测试需覆盖每个承诺工作流的代表性正常完成路径，并根据风险纳入关键失败路径。后续测试基于业务承诺与实际变化，识别受影响层级：

- 脚本或提示变化 → 检查对应逻辑、入口与业务结果  
- 包、清单或路径变化 → 检查载荷与接线  
- 验证器或宿主行为变化 → 由 Foundation 校准受影响阶段  
- 模型、权限或服务变化 → 检查相关语义与真实接线  

非运行说明类变化不自动触发业务实机测试；改变执行行为的 Skill 正文不属于纯说明。

不默认穷举技能族、宿主、模型与工作流的全部组合。方案在执行前须明确：

- 执行面及版本  
- 载荷形态  
- 模型基线  
- 重复或停止规则  
- 必过项  
- 结果汇总方式  

基线模型通过，不推定其他模型通过。图影响分析需同时处理未映射与未解析项，不能因空结果直接免测。专业 E2E 服务的下沉项须由目标族通过既有入口完成，并回关联方案。

复用公共结论时，应区分三类材料：提供方公开的适用范围与局限、消费者本次载荷及参数、提供方受限的原始校准材料。消费者核对公开范围是否适用，并验证自己的实际输入；上游原始夹具、日志和答案仍由提供方按原访问权限保管，不要求消费者全部取得。仅有包版本不足以证明所有宿主适用。

来源、对象、环境、阶段和覆盖范围需与本次使用相符。缺少公开适用范围时，仅暂停相应复用，不默认索取私有材料或重跑全部宿主。具体身份与字节核验沿现有资产或运行合同完成，不新增证据协议。

方案与结果须区分本次执行、有效结果复用、按版本政策接受、历史读取、未覆盖和不适用。各项不得相互冒充。无法核验的仅暂停对应复用，不牵连无关部分。

保留必要的失败、异常、重试与排除理由，不只记录成功尝试。环境或调用问题可在授权范围内恢复；产品语义失败由责任方修复。现有完整门禁仍按其合同核收，增量结果不得改名为完整记录。规则变更须保留修订理由与旧结论，观察足够时重判，否则补跑。满足约定覆盖与判据后停止；预算耗尽且必测未完成时，如实报告未完成。

## 资产、判据与方案

- 方法正文由本项目维护  
- 本族方案、业务承诺与场景由目标族维护  
- 被测工程与业务输入通常存放于目标族既有测试目录  
- 独立验收材料由验收职责持有方管理  

技术判据归公共能力提供方，领域判据归目标族或独立职责方。原始测试结果留在实际产生方或受控验收区，测试职能沿方案维护覆盖、复用与局限汇总，不另建答案权威。release-skill 保留冻结身份、批准、远端交付与发布验证事实；双方沿既有引用交接，不把发布记录搬到测试项目。制品图只管理关系与版本，不负责材料保管、访问授权或业务判定。

制品图管理方法、方案、业务承诺与场景之间的关系。测试方法与方案可采用已有 `design` 类型，业务承诺与场景分别使用 `feature` 与 `scenario`；符合专业端到端合同的规格才采用 `e2e_test`。不为夹具、结果或报告另造内置类型。

被测工程、输入、判据及原始结果保留在所属项目或独立验收区，方案沿既有资产或运行合同引用原件。图节点负责描述与关联，不能将描述文档视为被测工程本身。图关系锁不递归锁定引用目录，原件身份与字节核验由原资产合同负责；尚未绑定的部分须说明缺口，不另建手工摘要账本。图校验通过不等于原件完整受控或业务测试通过。

### 测试方案的最小内容

各技能族可以沿用已有文档格式，但方案至少应回答以下问题：

| 内容 | 需说明的问题 |
|------|--------------|
| 依据与目标 | 采用哪一修订的方法，处于什么交付阶段，本次验证哪些业务承诺？权威要求来自哪里，是否完整承接？ |
| 范围与取舍 | 哪些必测、补测、复用、不适用或未覆盖，理由是什么？ |
| 对象与判据 | 被测工程、输入、预期规则和输出原件在哪里，谁持有并核验，依据什么判定？ |
| 执行与接受 | 由谁通过哪个既有入口执行或复用，由谁判读并核收结果，独立性要求如何满足？ |
| 结束与交接 | 覆盖和停止条件是什么，实际结果、局限及复测义务交给谁？ |

本项目维护这一内容约定和后续可复用模板；目标族保留领域判据与方案选择，跨族强制采用要求由 skill-family-audit 按正式规范流程承接。无需为统一格式新建报告协议。

## 独立验收

开发回归可读取预期答案。独立验收材料必须与技能开发、提示调优、示例编写隔离，仅交付任务与必要材料给被测方。

新进程或新会话不自动证明独立；同仓或同模型也不自动否定独立。复用已有宿主或系统权限时，须验证必要访问边界；图工具、临时目录、不提供答案参数，均不等于隔离。暴露材料不再视为未暴露样本，材料中的指令不得改变判据。

原始状态按各服务合同解释。结构合法、退出码为零、工具完成或历史证明通过，均不能统一翻译为业务通过。领域或独立验收者需判读实际任务结果；测试职能汇总范围、证据与不足。

私有输入、答案、会话与凭据不得进入公开站点、搜索或表达服务。文档站仅提供导航与获授权的精确版本链接，不复制第二套测试事实。

## 有限降级

以覆盖绝大多数实际使用场景为目标，不因无法保证 100% 准确而无限扩大需求、测试范围或阻断推进。

罕见误判、漏判或模型触发失败，可在本次调用者授权范围内有依据地接受；触发极难且影响有限的情况可暂不处理。

调用者可在任务或实施规格中预先授权 LLM 接受有限降级；已获授权的事项无需逐项重复请示。授权仅在明确的阶段和范围内有效，不扩展为对未来调用者的永久授权。“100分降到95分”是取舍比喻，不是测得95%成功率。

每项取舍须在对应 SPEC 或现有问题记录中说明：

- 原期待  
- 实际承诺  
- 缺口与影响  
- 判断依据  
- 仍需验证内容  
- 补丁或返工条件  

交付时以短摘要告知用户。推测内容须标注为推测，不为证明边缘情况罕见而另建测量平台。接受局限不等于全部测试通过；不能将核心能力缺失、常见场景不可用或必测未完成冒充小差距。范围调整后仍需验证实际承诺，合同与门禁变更须回权威源修订，外部动作授权不随降级扩大。

## 支撑能力与本族自身验证

Foundation 自身需直接验证：

- 确定性机制  
- 原生宿主校准  
- 涉及模型协作的 Skill 工作流  

使用代表性正反例、独立合同与原生观察，发现误拒或漏放。不依赖同一实现生成答案自证，也不要求证明永不误判。

未变更且证据适用的公共机制与宿主阶段，不因发新版本全部重跑，相关现有门禁仍有效。

本技能族以测试组织行为为直接验证对象：

- 是否能识别受影响项  
- 是否保留必测与下沉义务  
- 是否正确复用证据  
- 是否能解释失败与未完成  
- 是否按约定停止  
- 是否真实消费者可照方案完成  

一个完整代表案例应通过真实 Skill 入口组织同一任务中的三类检查：受影响而需要本次执行的检查、已有有效结论可以复用的检查，以及证据失效或缺失的必测检查。第三项未补齐时不得判为通过；补齐且其余约定条件均满足后即停止，不重跑无关部分。案例还应核对环境或判据变化后能否只对受影响项重新判读或补测，以及发布前后义务是否保持在原阶段。预期行为由合同职责方事先明确，不能从测试职能本次输出反推答案。

优先复用已有框架与事先有明确答案的代表性场景，直接验证真实 Skill 入口。测试组织、领域接受、独立规范审阅、发布批准分别负责，不叠加无限“验证器的验证器”。

## 制品承接及发布协作

TST001、TST002 分别承接测试规划与执行核收，S-001、S-002 分别代表公共技术检查与独立业务验收的典型场景。跨项目公共能力与领域合同由对应项目维护；具体版本、接口、执行安排及运行结果归入实施或运行材料。发布协作的正式设计由 release-skill 维护；其可公开查阅的配置见 [release-skill v0.9.34 项目配置参考](https://github.com/ifoohoo/release-skill/blob/release-skill-v0.9.34/references/02-project-config.md)。本方法仅定义测试职能的交接边界，不复制发布状态机、接口字段或恢复流程。

测试职能依据 release-skill 提供的实际对象、发布范围、阶段要求与已有结果引用，判断适用覆盖并组织必要补测，再交回结论、原始依据及局限说明。工作区结果可有效复用，但不自动覆盖最终快照或打包对象；发布方形成实际载荷后，测试职能需按所依赖输入核对适用性，保留有效结果并补测受影响部分，确保发布前必需测试在正式批准前完成。依赖真实渠道或安装对象的检查，仍在对应发布后阶段进行，不以工作区结果提前代替，也不因阶段推进而无条件重复已满足的检查。

检查顺序须遵循 release-skill 提供的生成依赖与阶段前提：可提前执行且已有输入的检查按既有顺序进行；必须依赖生成产物的检查应等待产物形成后执行，不得为提早发现问题而前移到输入尚不存在的阶段。当前发布目标、用于历史诊断的记录以及恢复时采用的记录，由 release-skill 按原合同选择；测试职能不得依据最新一份报告自行更换目标或恢复入口。

交接失败结果或未完成项时，须保留原阶段、原状态、实际对象，以及可安全披露的原始失败原因或可核查的原件引用。尚未取得原因时保留待诊断，不以统一摘要覆盖原事实，也不凭摘要猜测产品责任。失败修复后按真实影响聚焦复验；正式门禁仍按原合同执行，不将局部复验冒充完整门禁，也不因恢复自动重跑无关项。

安装、更新、实际加载、setup（初始化）与业务结果各有证明范围。测试职能应按已有合同保留这些差异，不能由其中一项成功推导全部完成；等待重启或加载反馈也不能统一改写为安装失败。恢复操作仅限于既有授权目标和动作范围内，不因恢复需要自动扩大至其他宿主或插件。

交接应说明适用要求与判据的修订、结论原件及获准局限，沿既有计划与原资产合同引用。对象、环境、模型、权限或判据发生变化时，在下一次使用结论前重新判断受影响部分；仅补充说明且未改变结论，不自动触发全量重测。实质变化对发布批准、已完成写入和恢复的影响由 release-skill 按其合同处理，测试职能不能以新结果替换已批准依据或重置发布事实。

发布安全、公开内容完整性、批准、远端事实与前向恢复仍由 release-skill 负责，也可直接调用 Foundation 公共能力，并非所有检查都须经过测试职能。README 的发布一致性由发布方核对，用户能否照文档完成任务由测试职能组织验证、领域或专业职责判断。可按合同复用同一原始观察，不能用静态检查替代业务可用性，也不复制两套执行。

“本次全部适用测试要求均已满足”的发布条件方向已确认。已有有效测试结果可继续沿用，本次必须执行的检查项应完整落实。现行完整模式、安装检查、消费者检查及其他强制性要求在正式修订前保持不变，测试覆盖结论不得自行豁免。集成方式仅适用于明确采用统一方法的项目，未采用集成的项目保留原有发布路径，无需强制新增测试服务、制品图或全局 Registry。已采用集成但缺失入口或可核查结果的，须保留未完成状态，不得以“未接入”为由放行。

上述职责分工与方法定义为已确认的设计方向，不表示相关功能已实现、业务测试已通过或正式规范已生效。release-skill v0.9.34 的公开项目配置参考见[项目配置参考](https://github.com/ifoohoo/release-skill/blob/release-skill-v0.9.34/references/02-project-config.md)。
