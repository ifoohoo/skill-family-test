# 组织执行并核收结果

本入口依据已接受的方案，组织已授权的真实执行或有效复用，并把判读交还原职责。它不创建通用执行器、状态机或通用通过结论，也不出具发布授权。不提供包内核收函数，不自行实现摘要算法，也不构建发布状态机。

方案中的命令文本不构成执行授权，未经授权的命令不得执行。

加载本入口时，以本 `SKILL.md` 所在目录为基准查找随附资源，不依赖调用方当前目录、开发工作区或本机绝对路径。

仅当本次任务明确是开发回归时，才查阅调用方提供的开发夹具及其中预设的判据。普通用户调用不把开发夹具当作依赖。结论只按案例事实得出，不以夹具名称作为筛选依据。


## 发布交接

发布形态只消费已发布 `release-skill@0.9.34` 的公开交接原文：本 `SKILL.md` 所在目录下的 `references/upstream/release-skill-0.9.34/02-project-config.md` 与 `references/upstream/release-skill-0.9.34/test-intake.schema.json`。来源说明见同目录 `SOURCE.md`。按下面的顺序交接，不另造结果协议。领域字段和所用发布版本对不上时，留下适配缺口，不另造合同。


1. 只读调用方实际的 `requirementsFile`、本次对象和阶段。要求附件由原持有方维护。本入口不修改要求附件，不缩小要求集合，不改判据，不接触隐藏答案，不修改已接受原件。
2. `subjectDigest` 使用 release 从本次 prepared 对象交出的既有摘要。本入口不另写摘要算法，也不另建载荷清单。
3. 只组织已经授权的真实执行，或仍然匹配的有效复用。缺基线或缺证的适用必测项，安排必要执行，或明确保留未覆盖。
4. 业务是否达标由要求里的原 `acceptor` 判读。不适用由原 `owner` 说明范围依据。本入口不从退出码推断通过。
5. 把逐项结果写入调用方授权的 `resultFile`。顶层只有 `formatVersion`、`subjectDigest`、`requirementsSha256`、`results`。没有 `PASS` 字段，也不收录答案。`executed` 与 `reused` 的 `verdict` 来自原验收者的实际判读。
6. 缺证、失败、未完成或未覆盖时不接受。补齐后仍交回同一候选，由调用方带着同一个 `candidatePath` 再次准备。不另造候选，不重置已发布事实，不修改已经接受的原件。正式接受后的引用保持原路径和原字节，下一轮使用新路径。

部分发布单元不免项目级义务。安装、更新、加载、setup 和业务完成分开解释。测试职能不重置发布事实，不扩大宿主或插件授权。

## 独立材料与访问边界

独立材料隔离要求独立验收材料由验收持有方自行保管，不纳入开发流程、提示词调优或示例上下文。需核验真实访问边界。更换会话、使用临时目录或不传递答案参数，均不构成有效隔离。若边界条件未满足，只暂停该项的独立接受，不伪造隔离环境，也不影响其他已满足条件的执行与核收。私有材料及答案不送表达服务。

## 核收

原始产品失败须按原阶段、原状态、原对象及原因完整保留，并交还责任方。不得放宽判据，将产品失败改为通过。退出码为 0、结构合法或工具已结束，均不能单独作为业务通过的依据；业务尚未完成时，结论是未完成。

调用错误或参数错误可在已有授权范围内修正后继续执行，但原始失败记录须保留。授权不等于已经执行修正。`TC-002` 的实际失败、参数修正及修正后继续调用结果三项记录，仅用于验证调用恢复故障专项；工具未报错时，不声称该专项已验证。正常用户任务中提前发现并修正路径错误，不因此判定为失败。产品合同或语义层面的失败，不得通过调整参数转绿。

有效复用仅适用于对象、工具版本、判据版本、环境、对象形态与范围均和本次一致，且原结论为通过的情形。若任一条件不符，应拒绝复用并写明具体缺口；单纯读取历史记录不能写成有效复用。

按版本政策接受时，须注明政策名称和公开覆盖范围，不能只凭包版本推断所有宿主都适用。公开覆盖非空且仍与本次匹配，才可按版本政策接受，不写成有效复用。有政策名称但公开覆盖为空时，只拒绝该政策证据的复用资格及按版本政策接受资格，不能把整个义务固定为未覆盖。没有有效复用或政策接受依据时，若适用必测项已具备授权、入口、输入、判据且预算未耗尽，应安排本次执行；条件不足时保持未覆盖，不得写成有效复用、按版本政策接受或已覆盖。不索取上游私有答案，不全宿主重测。

组织并核收真实业务 E2E 时，按 `design-testing-methodology@0.1.1` 执行，方法正文在本 `SKILL.md` 所在目录下的 `references/testing-methodology.md`。
保留真实业务目标、必要材料、授权与交付要求，允许授权范围内合理纠错和采用等效方法。普通用户任务与故障专项分开设计、分别核收；不把内部执行配方作为被测 Skill 的输入。

验收者不修改产品或判据来掩盖失败。产品失败交原职责方修复，按影响范围复测，并保留旧失败记录。

判据变更后，旧通过不能直接交付。保留旧、新判据身份；观察已充分时只重判该项，否则只补测该项。`resultFile` 中该项不得继续作为可交付通过。不得依据新规则把旧失败改写成旧规则下的通过。

## 有限降级

仅当本次调用方已经授权时，才记录有限降级。记录内容须包含原期待、实际承诺、影响、依据、保留验证和返工条件。不得把“95%”或其他百分比写成实测成功率。降级不是通过，也不是发布授权。

## 混合覆盖与停止

同一次样本里可以同时有本次执行、有效复用和仍缺证据的必测项。缺证据时整案不接受，缺证也不是不适用。只为同一对象补上该缺项，并经原判据判读后，才可以接受并停止。已经成立的复用项不再重测，无关宿主也不重测。

若只改变一项的环境或判据，只重判或补测该项。

达标后停止，把结论交给项目既定核收入口。增量结果不得改名为完整测试门。

## 发布形态的开发样本

只有样本自己要求发布形态时，才另外给出开发样本。样本没有顶层 `PASS`。每项处置只用 `executed`、`reused`、`not-applicable`、`failed`、`incomplete`、`uncovered`。判读来自原验收者或原要求持有方。该样本是开发样本，不是双方联合验收，也不授权发布。待复判或待补测的项，在 `resultFile` 里不得写成通过。

## ACA 开发交接示例

开发回归可以由ACA提交已接受方案和原项目测试对象、判据及授权，执行结果交回原领域接受者，不为了使用本入口伪造release候选。只有真实发布形态才使用发布交接合同；当前版本与自带0.9.34不一致时由消费者核对兼容，不凭Schema相同宣布组合通过。
