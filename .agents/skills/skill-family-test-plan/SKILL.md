# 制定本轮测试方案

本技能只负责制定和核验测试方案，**绝不在规划阶段运行被测产品、执行测试命令、修改业务代码，也不预填“通过”结论或签发发布授权**。方案中写出的命令与入口仅作执行计划记录，需经调用方确认授权后交由 `skill-family-test-run` 组织运行。

加载本技能时，一律以当前 `SKILL.md` 所在目录为基准读取随附参考（如 `references/testing-methodology.md`，修订身份 `design-testing-methodology@0.1.2`），不依赖调用方工作目录或本机绝对路径。仅当本次任务明确是开发回归时，才查阅调用方提供的开发夹具及预设判据；普通用户调用不把开发夹具当作依赖，也不按夹具名称筛选结论。

## 一、收齐规划输入与交付阶段

动笔前先核清五项输入：**交付阶段**、**本轮变更范围**、**业务承诺与权威要求**、**既有测试证据**，以及**被测资产与判据位置**。交付阶段直接决定方案的接受尺度：

- **开发基线（`development-baseline`）**：围绕当前开发承诺与回归风险选测，普通开发不默认追加独立验收。
- **候选交付（`candidate-delivery`）**：按候选合同核对覆盖范围，允许保留明确披露的未验证项，但不得据此声称已通过稳定业务验收。
- **稳定业务验收（`stable-acceptance`）**：验证对外正式承诺，需要独立验收的环节必须使用真实隔离材料，不允许拿候选结论或未覆盖项顶替。

若目标技能尚处于接入重型工程化之前的最小原型阶段，或刚遇到“换一份材料就失效”的情况，先要求准备至少 2 份异构真实样本与只读判定条件，用 `sft eval-smoke` 验证跨样本泛化与修改前后回归，防止针对单一样本硬编码打补丁。

## 二、按变更影响选择测试层级与组合

对照同目录 `references/testing-methodology.md`（`design-testing-methodology@0.1.2`），从本轮改动的脚本、提示词或配置出发，结合直接调用方、下游消费者和历史回归记录选择正反测试组合，不盲目穷举全部宿主与模型：

1. **首次建立基线**：尚未建立基线的工作流，必须同时安排代表性正常完成路径（`normal`）与关键风险失败路径（`risk-failure`），状态均定为“本次执行”。
2. **增量变更选测**：
   - **脚本或内部纯函数改动**：安排就近单元测试覆盖正常与边界分支。
   - **包配置、公共能力接线或参数组合改动**：从真实公共入口安排集成测试，验证对象绑定与失败传播。
   - **Skill 指令或业务语义改动**：安排真实用户条件下的端到端（E2E）业务场景验证，将普通用户任务与故障恢复专项分开设计，不向被测 Skill 塞入内部通关配方。
3. **上游公共能力与本族职责切分**：优先调用项目既有检查与 Foundation 已发布公共接口，但调用前必须核实精确版本、适用对象与环境一致。Foundation 的宿主校准只证明对应宿主加载机制成立，不能代替本技能族自身的载荷配置、调用参数与业务语义验证；本族也不重复测试上游内部算法。
4. **部分单元与多阶段对象**：仅发布部分单元不免除项目级检查义务。工作区、最终打包载荷、公开发行渠道与消费者安装对象须分别判断；后阶段对象尚未生成时，对应检查保持“未覆盖”，不能拿工作区测试结果提前顶替。

## 三、逐项划分材料状态与复用边界

方案中的每一项测试都必须写明：**所属层级**、**测试对象与输入原件**、**执行入口**、**判据持有人**、**停止条件**，并从以下状态中唯一选定一项且写清依据（规划阶段禁止出现 `passed`）：

| 材料状态 | 适用条件与核对边界 |
| --- | --- |
| **本次执行（`execute`）** | 无可复用证据或政策依据，且授权、入口、输入、判据齐备、预算未耗尽的适用必测项。 |
| **有效复用（`reuse`）** | 对象身份、对象形态、工具版本、判据版本、运行环境与覆盖范围六要素均与本次一致，原结论为通过，证据原件未被篡改，且非单纯历史读取。 |
| **按版本政策接受（`policy-accept`）** | 具备明确的版本政策名称且公开覆盖范围非空、与本次场景匹配（不可仅凭包版本号推定全宿主适用；若公开覆盖为空，只能拒绝政策复用并视执行条件转为本次执行或未覆盖）。 |
| **历史记录读取（`historical-read`）** | 仅读到过往运行记录而未满足本次六要素核验，不能冒充有效复用。 |
| **可选显式跳过（`explicitly_skipped`）** | 仅限 `optional: true` 的可选测试，经维护者确认本轮跳过，须写明批准人、原因、适用边界、残余风险与兜底必检门禁；必选门禁严禁跳过。 |
| **未覆盖（`uncovered`）** | 缺少执行前提、预算耗尽、仅锁制品图说明节点而无真实原件，或存在**未映射、缺判据、要求冲突**（后三类必须保持可见并退回原权威裁决，不得私自豁免）。 |
| **不适用（`not-applicable`）** | 仅在原要求持有方已给出明确范围排除依据时使用；宿主未变但缺乏基线证据时，不得自行标为不适用。 |

## 四、独立材料隔离与方案机器核验

1. **真实访问隔离**：独立验收材料由验收持有方单独保管，严禁进入开发调试、提示词优化、公开示例或外部表达服务。仅换开新会话、换临时目录或不把答案放进命令行参数，都不构成有效隔离；隔离条件未满足时只暂停该项独立验收，不影响其他就绪条目的规划。
2. **CLI 确定性校验与验收条件直接行为核查**：外部项目按“**在项目或环境中安装公开 npm 包 `skill-family-test`（提供 `sft` CLI）+ 在 AI 宿主安装 `skill-family-test` 插件**”双通道接入。当工作区或环境已安装公开 npm 包 `skill-family-test`（`pnpm add -D skill-family-test` 或 `npm install -D skill-family-test`）时，在交付结构化方案前运行以下命令核验分层覆盖、验收条目（`AC-*`）直接行为映射与设计原件摘要：
   ```bash
   npx sft validate-plan --root /absolute/project/path --input test-plan.json --format markdown
   ```
   每条声明的 `AC-*`（支持字符串编号或 `{ "id": "AC-1", "description": "...", "requireDirectBehavior": true }`）不得仅靠 `unit-mock` 模拟测试充数，应至少绑定一条具备真实行为验证层（如 `integration`、`e2e`、`cli-smoke`、`direct-behavior`，或显式标注 `verificationDepth: "direct"`）的测试项；需要将该项核查升级为硬阻断时，可追加 `--strict-ac-behavior`。若当前仅做纯文档规划且未安装 CLI，按上表逐条核对覆盖关系与停止条件后直接交付方案。达到约定覆盖范围与判据即停止，不向无关宿主或模型蔓延；获准的有限降级须写明原期待与实际差距，不得折算为虚构的实测成功率。
