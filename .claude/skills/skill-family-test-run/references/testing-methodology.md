# 技能族全生命周期测试方法

## 公开投影说明

公开打包时，构建脚本会将本文原样投影为各技能目录下的 `references/testing-methodology.md`，修订身份保持为 `design-testing-methodology@0.1.2`。插件包内的投影副本禁止手工单独修改。

## 目的、分工与要求来源

本方法规定技能族在每次新建或迭代中应当测什么、怎么选测、如何复用既有观察、由谁判定结果，以及满足什么条件后立即停止。它覆盖测试方案制定、最小样本探针、测试资产组织、授权执行、结果核收与增量复测全过程。

各协作方的权责边界如下：

- **`skill-family-test`（测试职能，`support` 支撑分层）**：识别本次受影响范围，组织测试规划、授权执行、增量复用核算与结构化收据归集；通过公开 npm 包 `skill-family-test`（提供 `sft` CLI）与多宿主插件 `skill-family-test` 配套交付。日常开发可独立调用，不依附发布流程，且测试核收通过不自动签发发布批准。
- **`Foundation`（基础工程与公共机制）**：提供契约校验、闭世界文件登记、受管投影、子进程监督，以及承诺宿主的安装、发现与加载校准能力。
- **目标技能族或独立验收持有方**：定义并持有领域业务判据与隐藏验收材料，对业务结果是否真正达标作出最终判读。
- **`skill-family-audit`（独立审计）**：负责跨技能族规范适用性审查与独立合规审计。

测试要求来自四处权威输入：目标族的业务承诺、正式适用规范、项目既有强制门禁，以及调用方指定的交付阶段；进入发布流程时，候选对象、发布单元范围与阶段交接要求由 `release-skill` 提供。测试职能负责把上述要求逐项承接到测试方案中，不得私自篡改业务承诺或放宽强制门禁。遇到未映射、缺判据或彼此冲突的要求时，必须原样保留为“未覆盖”并退回原权威裁决，禁止默认免测；仅发布部分单元也不自动免除项目级检查义务。

## 测试分层与三种交付阶段

脚本断言、大模型协作与人工审阅只是执行手段，不是测试层级。规划时按验证目标划分为八个环节，每个环节都需交代清楚测试对象、检查方式、判定依据与实际覆盖边界：

| 测试环节 | 测试职能负责事项 | Foundation 公共支撑 | 目标技能族保留职责 |
| --- | --- | --- | --- |
| **最小原型探针** | 校验至少 2 份异构真实样本与修改前后回归对比（`sft eval-smoke`） | 暂不介入重型骨架，避免过早引入工程负担 | 准备代表性正常与边界输入样本，确认核心指令路径成立 |
| **需求与方案** | 梳理业务承诺、必测项、复用依据、可选跳过边界与停止条件（`sft validate-plan`） | 提供公共能力目录与适用前提说明 | 评估业务风险，定义领域判据与验收责任人 |
| **单元与组件** | 针对受影响的纯逻辑与边界分支安排就近单测 | 提供公共契约 Schema 与标准测试向量 | 维护领域算法、脚本逻辑与异常分支断言 |
| **集成与接线** | 从真实公共入口核验参数传递、模块组合与错误传播 | 提供稳定的公共 API 与输入输出契约 | 保证自身消费接线与下游输出格式一致 |
| **候选载荷与静态门禁** | 核对实际打包产物、文件闭合与宿主投影目录 | 提供闭世界登记、摘要锁、投影校验与静态加载检查 | 维护项目专属载荷白名单与生成配置 |
| **宿主与运行环境** | 识别受影响的宿主阶段，调用加载检查或核验公开校准证据 | 提供受支持宿主的发现、加载检查与实机校准基线 | 验证宿主特有的插件清单接线，如实披露未校准宿主 |
| **真实业务与人工验收** | 按真实用户条件组织端到端（E2E）正常路径与风险失败路径 | 提供路径收容隔离与有界进程监督 | 判读模型与工具协作产出的业务质量、交互体验或视觉结果 |
| **文档可用性与发布核收** | 组织照文档安装使用的可用性验证，归集候选收据与未决项（`sft record-run`） | 提供基础文档存在性与身份一致性诊断 | 发布方核对公开边界、版本号与批准记录，主导远端发布 |

静态语法合法、宿主成功发现加载、模型在真实任务中交付合格业务结果，是三件不同的事，不能用前一层通过推断后一层已经成功。

为防止把日常开发自测与正式对外验收混为一谈，方案必须声明当前所处的交付阶段：

| 交付阶段 | 验收尺度与允许边界 |
| --- | --- |
| **开发基线（`development-baseline`）** | 验证当前开发切片的功能承诺与直接回归风险，普通开发不默认追加独立隔离验收。 |
| **候选交付（`candidate-delivery`）** | 按候选范围核对检查项，允许保留明确列出的未验证项，但严禁把候选状态宣传为稳定业务验收通过。 |
| **稳定业务验收（`stable-acceptance`）** | 逐项验证对外稳定承诺；凡需独立验收的环节必须使用未污染的隔离材料，不允许存在未覆盖必测项。 |

## 真实用户条件下的端到端（E2E）准则

1. **从公开入口给出真实任务**：测试必须从用户实际可见的公开 Skill 入口启动，只提供业务目标、必要背景材料、真实运行环境授权和交付要求，严禁塞入隐藏标准答案或“先调哪个脚本再调哪个参数”的内部通关配方。
2. **保留智能体自主恢复空间**：在公开合同与权限边界内，允许被测 Skill 自主查阅参考文档、向用户澄清必要前提、修正局部调用参数或选用等效路径，不预设唯一正确的工具调用轨迹，也不为测试方便强迫模型先犯一个错误。最终按“业务目标是否达成 + 必经安全/审批边界是否守住”共同判定。
3. **正常任务与故障专项分列**：普通用户路径与故障恢复专项分开设计、分别核收。若在普通任务中模型提前识破路径问题并顺利完成，判普通任务通过，但只要没有真实发生“工具报错 -> 参数修正 -> 继续调用”，故障恢复专项就必须保持“未验证”。
4. **工程化前防过拟合扩样**：新建技能接入完整工程骨架前，或遇到换一份真实材料就失效时，必须把新旧材料一起纳入最小样本集（至少 2 份结构或场景异构的真实输入），通过 `sft eval-smoke` 对比修改前后表现，严禁针对新样本硬编码打补丁而把原本通过的旧样本改坏。

## 选测、复用、显式跳过与停止规则

首次建立测试基线时，必须覆盖每个承诺工作流的代表性正常路径与关键风险失败路径。后续迭代按实际变更识别受影响层级：脚本或指令逻辑改动测对应单测与业务行为，清单或路径改动测载荷与宿主接线，模型或外部服务变动测语义一致性；纯非执行类说明更新不自动触发全量业务实测（但改变智能体行为的 `SKILL.md` 正文修改属于逻辑变更）。

方案与收据严格区分以下状态，任何两类状态均不得混同：

- **本次执行（`execute` / `executed`）**：授权与前提齐备的当次实测项；退出码为 `0` 但业务目标未完成时只能记为 `incomplete`，绝不算通过。
- **有效复用（`reuse` / `reused`）**：对象身份、对象形态、工具版本、判据版本、运行环境与覆盖范围六要素均未变，原结论为通过且证据文件 SHA-256 摘要核验无篡改。
- **按版本政策接受（`policy-accept`）**：引用公开非空且与本次匹配的宿主或组件校准政策（消费者只需验证自身载荷与参数，无需索取提供方私有校准日志；仅凭包版本号不能推定全宿主适用）。
- **历史记录读取（`historical-read`）**：仅查阅过往记录，不满足本次复用核验条件。
- **可选测试显式跳过（`explicitly_skipped`）**：仅适用于标记了 `optional: true` 的可选测试，经维护者确认跳过时，必须记录批准人、跳过原因、适用边界、残余风险与仍在兜底的基础必检门禁；其结论固定为 `not-evaluated`，**绝不混同于 `passed`**，必选权威门禁严禁跳过。
- **编排/环境未执行（`not_executed` / `orchestration_error`）与产品失败（`failed` / `product_failure`）**：因 `PATH`、Node.js 版本或参数拼写导致未跑入产品逻辑时记为 `not_executed`（修环境后重跑），产品违反合同或判据时记为 `failed`（保留原失败记录交回开发修复）。
- **未覆盖（`uncovered`）与不适用（`not-applicable`）**：缺前提或预算耗尽保持 `uncovered`；仅原要求持有方提供明确范围排除依据时才可标为 `not-applicable`。

达到约定的覆盖范围和判定标准后立即停止，不向无关宿主或模型组合外溢。

## 从本批变更推进到稳定验证

1. **核实前提与局部隔离**：先确认本批改动目标、输入材料与所依赖公共能力的精确发布版本及适用环境。若某项外部依赖或对比基线暂缺，只暂停受其阻塞的测试条目并注明恢复条件，其余具备条件的正反用例照常推进。
2. **沿调用链选定正反参数族**：从被修改的函数、Schema 或 `SKILL.md` 段落出发，结合直接调用方、输出消费者和历史回归样本选出相关参数组合，同时保留原正常路径与拒绝路径断言，禁止只跑一条新写的正常正例就收工。
3. **返工聚焦验证与增量失效重算**：开发与修复期间只跑覆盖当前改动的聚焦测试；修改落定后，调用项目官方生成命令刷新受影响的受管投影或锁文件，并用 `sft invalidate-changed` 对比文件 SHA-256 摘要，精确重跑受波及用例、保留未受影响的已核验观察。判据版本升级后，旧规则下的通过记录自动失效：原始观察足够时按新规则重判，不足时定向补跑。
4. **稳定快照集中审阅与批末一次门禁**：聚焦测试与派生文件齐备后，在同一个冻结快照上执行集中独立审阅、一次分诊并统一返工；全部直接修复项验证通过后，在批次末尾运行一次完整权威门禁，禁止每改一个小问题就把全套慢门禁重跑一遍。出现慢测试瓶颈时，优先基于已有耗时日志或环境中可用的 `test-performance-optimizer` 分析重复初始化与串行等待，不为证明“确实很慢”而反复空跑全套。
5. **结构化核收与可读交付**：使用 `sft record-run` 与 `sft render-report` 产出绑定摘要的收据与结论前置的 Markdown 报告，把实测通过、有效复用、可选跳过、环境未执行和产品失败分栏列清。

## 资产责任、独立验收与有限降级

- **资产归位**：测试方法与公共 CLI 由本仓维护；各技能族自身的测试计划、业务承诺与夹具留在各自仓库；制品图（`artifact-graph`）只维护文档追溯关系与版本锁，不充当测试原件仓库或权限隔离机制（仅锁说明节点而无真实原件时仍属未覆盖）。
- **独立验收真隔离**：独立验收材料与标准答案由验收职责方单独持有，严禁流入开发会话、提示词调优、公开夹具或外部润色服务。单靠新开会话、换临时目录或不传答案参数不算有效隔离；隔离无法证明时只保留开发回归结论，暂停宣称独立验收成立。
- **有限降级记录**：针对极罕见的边缘误判或自然语言触发波动，可在调用方针对当前任务明确预授权的前提下接受有限降级，但必须如实写明原期待、实际承诺、影响范围、判断依据与后续触发返工的条件，绝不能把核心功能缺失、必测未完成或常见路径报错包装成“小幅降级”，也不得把比喻性的取舍说成“95% 实测成功率”。

## `sft` CLI 确定性校验与 `AC-*` 直接行为映射设计

`packages/skill-family-test` 通过统一可执行入口 `sft`（退出码约定：`0` 核验通过、`1` 阻塞/门禁不通过、`2` 参数非法或路径越界违规）把上述方法规则落实为五项零网络确定性命令：

| 子命令 | 核心校验对象 | 关键防伪与直接行为规则 |
| --- | --- | --- |
| `sft validate-plan` | 测试方案结构、`bindings` 摘要、`acceptanceCriteria`（`US-033`） | 核对磁盘设计/需求原件 SHA-256 与方案一致，拒绝规划阶段预标 `passed`；区分真实行为层 `DIRECT_BEHAVIOR_LAYERS`（`integration`、`e2e`、`cli-smoke`、`direct-behavior`、`host`、`payload`、`scenario`、`acceptance` 或 `verificationDepth: "direct"`）与纯替身层 `MOCK_ONLY_LAYERS`（`unit-mock`、`mock`、`stub`）。对仅由模拟层覆盖的 `AC-*` 默认发出中文告警，传入 `--strict-ac-behavior` 或声明 `requireDirectBehavior: true` 时升级为 `mock_only_coverage` 硬阻断；`unit` 间接单测在未开启严格模式时保持向后兼容。 |
| `sft record-run` | 测试执行结果与收据生成 | 隔离 `explicitly_skipped`（结论恒为 `not-evaluated`、`passed: false`）与 `orchestration_error`（环境未跑进被测产品），拒绝无有效判据或仅靠静态存在充当通过。 |
| `sft invalidate-changed` | 变更前后文件摘要与判据版本 | 逐一比对测试项依赖文件的 SHA-256 与 `criterionVersion`，精准保留未受影响旧证、仅使受改动波及或原件被篡改的条目失效。 |
| `sft eval-smoke` | 工程化前最小代表性样本集 | 强制至少 `2` 份结构/场景异构样本且校验修改前后交叉回归，防止针对新样本打硬编码补丁弄坏旧样本。 |
| `sft render-report` | 结构化核收结果 JSON | 确定性生成结论前置 Markdown 摘要，分栏展示实测通过、有效复用、可选显式跳过、环境未执行与产品失败，以及验收条件直接行为覆盖告警。 |

## 发布协作边界

日常开发测试无需等待发布工具介入；进入正式发布流程时，按 `release-skill` 公开配置约定交接（参考 [release-skill v0.9.34 项目配置参考](https://github.com/ifoohoo/release-skill/blob/release-skill-v0.9.34/references/02-project-config.md)）：

- 发布工具提供打包后的候选对象与 `subjectDigest`，测试职能核对哪些工作区证据仍适用、哪些因打包或路径映射需在候选载荷上补测，确保发布前必测项在批准前闭环；依赖真实远端渠道或消费者隔离安装的检查留在发布后对应阶段执行，不提前拿工作区结果顶替。
- 发布安全校验、公开文件白名单、人工批准、远端推送标签及异常前向恢复均由 `release-skill` 主导；测试收据只如实交付覆盖与判读事实，不重置发布状态，也不越权签发上线许可。
